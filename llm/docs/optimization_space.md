# 优化空间分析 — 对齐官方还差什么（2026-09-24）

## 当前位置

| | 我们 kv6_stacked | 官方模型（同板同日同 harness） |
|---|---|---|
| decode/步（poke 后） | **268ms (py) / 278ms (C++)** | 290ms @H29；随历史线性涨（H255 无 poke 437ms） |
| 官方历史标尺 | — | ~202ms（4.9 tok/s），今日环境未复现（qwen_chat 自测 335ms） |
| 区结构 | 741 区（121 个 100K-1MB 大区） | 1330 区/run，9548 函数，全部 <1MB |
| .text | 522MB（8 段） | 130MB（split6 + inst_opt） |
| 滑窗 | w32 恒定（不随历史变慢） | 无窗口（KV 全保留，物理上必变慢） |

**结论：官方两个结构性优势——① 编译器排程密度（.text 4×小=每步指令流开销 4×小）
② 无窗口（精度优势）。我们的窗口是速度护城河，也是质量负担。**

## 已证伪的方向（勿重跑）

- "每区 2.45ms 固定税"：排队等待伪影（无剖析净计时 13ms/层；nopos/nokv 无差异）
- 输出/输入宿主缓冲同步税、物理地址（mmz +64MB 扰动无变化）、地址烘焙常量
  （快→慢地址交换后仍慢）、flush_cache（运行期实测全 KB 级）、C++ vs python（无差）
- 词表剪枝 30K（-10.7% 体积只换 2% 速度）
- T2 peephole 直接开（全模型 sim cos=0.9396 数值不过，见 known_issues）

## 剩余 18ms（268→250）的杠杆，按性价比排序

1. **官方模型对齐复测**（半天）：官方 202ms 标尺到底什么条件——用 qwen_chat 官方二进制
   在黄金窗口+poke 下扫 H∈{5,16,29,64}×max_new_tokens，拿到真标尺再定目标松紧。
2. **窗口 32→24/16**（小时级）：K 宽度直接减注意力 GEMM 量。w24 预估 -15~25ms。
   **必须先过质量验收**（见 known_issues——w32 质量都还没正式验收）。
3. **T2 peephole 复活**（1-2 天）：mini 逐位过、全模型 cos=0.9396 不过 →
   疑点在区边界配对变换（Dequant→GNNEStore 的值域假设）。修复后 -2.6% .text，
   按指令流开销占比折算 ~-5-8ms。
4. **区融合对齐官方**（天级）：官方把 LN/Softmax/rope 都融进大区，我们这些是独立
   CPU/小 GNNE 区。在 proj82 加 fuse 规则（Slice/GetItem/Reshape 穿越量化 commute 先行）。
5. **更多 QoS 寄存器**（半天，碰运气）：0x911/0x913 域逐寄存器扫（参考 probe_clk.sh 模式），
   官方只公开了 3 条，未必是全集。
6. **指令流优化 T3/inst_opt 等价物**（周级，终极）：.text 522MB vs 130MB 的差距是
   每步配置发射密度。官方靠 MMU 描述符+SSR 外提+JAL 循环。GNNE ISA 已全掌握
   （tools/isa_spec.json + 官方 fn0 解码样本），工程大但天花板高（200ms 以内唯一路径）。
