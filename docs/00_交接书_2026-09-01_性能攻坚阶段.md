## 一、任务与当前结论

在 01Studio CanMV K230（大核 C908@1.6GHz RVV1.0，Linux 6.6.36，2GB LPDDR4）上做**离线中文语音助手**：KWS → ASR → LLM(Qwen3-0.6B) → TTS，全程本地推理，响应 <5s 级。

**已达成（全部实测）**：
1. GNNE（KPU）真实点亮并跑通推理——输出正确中文（思考模式正常）、无乱码、无死机
2. 混合架构跑通：**prefill 走 KPU、decode 走 CPU**
3. 模型定稿 **Q8_0**（论证见 §三）
4. 所有测试经 safe_run（WDT 护航）落盘 /mnt/data，板子可持续无人值守实验

## 二、拍板决策（勿再摇摆，理由见 §三/§五）

| 决策 | 结论 |
|---|---|
| LLM 引擎 | llama.cpp（RVV 后端已深度优化：nrc=2 修正 + unroll×4） |
| LLM 模型 | **Qwen3-0.6B Q8_0**（604MB），性能+精度双赢 |
| 推理架构 | **混合**：prefill(M≥32) 走 KPU daemon；decode 留 CPU |
| 全 KPU decode | 已判死，勿回头（int8 权重=1.8x 数据 + daemon 往返，上限 2.2-2.5 t/s 且赢不过 CPU） |
| PLL 超频 | 已判死（双系统镜像上动 PLL3 两次挂死整机，小核隐藏依赖），**DRAM 也不是瓶颈，勿试** |
| TTS/ASR/KWS | 走 KPU/nncase，kmodel 现成（卡上 zh_fastspeech 14.8MB + multi_kws 370KB；ASR 用 Whisper encoder） |
| 优化原则 | 性能优先，精度其次；**模型部署后固定，允许写死/硬编码优化**（用户明确批准） |
| decode+TTS 并发 | 产品形态：CPU decode 累计句子 → 逐句交 KPU TTS 并发；prefill 也在 KPU（见 §六 P3） |

## 三、当前性能全景（2026-09-01 全部实测，可信基线）

| 指标 | 数值 | 说明 |
|---|---|---|
| **CPU decode tg32**（Q8_0, -t 1） | **2.46 ± 0.02 t/s** | 新 asm 内核（v2，见 §六 P0'）；旧内核 2.22-2.36；fs_anchor 修复后干净退出 |
| CPU prefill pp64（Q8_0） | 4.20 ± 0.01 t/s | nrc=2 未动，不变 |
| **混合 prefill pp128**（KPU+CPU） | **10.84 ± 0.16 t/s** | Q8_0 模型 + Q8 源 kmodel + daemon 模式 gnne_regs/preload 优化；历史 9.89→10.84 |
| 混合 decode tg16 | 2.45 t/s | 混合模式 decode 仍 CPU，吃新内核红利 |
| KPU 全 decode | 1.1-1.2 t/s | 已放弃（§二） |
| DRAM 单核连续读墙 | **6.06-6.32 GB/s**（vle8m8 实测） | decode GEMV 1.83GB/s ≈ 29%——**墙不在 DRAM，在 load 延迟** |

**decode 每 token 精确解剖**（tmpfs 计时仪，新内核 424ms/token 中位）：
- 196 个 GEMV delta：**316ms**（内核 ~290ms @21ns/blk + 算子间 ~26ms）
- result_output 间隙：**105.9ms = lm_head GEMV ~100ms（151936×1024 Q8_0 ≈165MB @1.5GB/s）+ 纯框架 ~6ms**
- **⚠️ 旧诊断修正：115ms"间隙"不是纯框架——~95% 是 lm_head 真实计算**；持久图优化上限 ~10ms/token
- 采样不是成本（贪心 vs 默认相同；Zfh 硬件 fp16 让软转也不是成本）
- **GEMV 内核已延迟约束**：微基准热 27c/blk、流式 30c/blk；向量管线地板 ~17c/blk（vwredsum 8c/blk 是大头）；剩余 ~13c/blk 是 load 延迟暴露——32 个向量寄存器装不下足够在飞 load，v4/v5 软件流水线与 prefetch.r 实测均无增益

## 四、架构与板上资产

### 4.1 混合推理架构

```
llama.cpp(CPU: 非GEMM+decode GEMM)
   └─ mul_mat (M>=32, KPU_HYBRID=1)
        └─ unix socket /tmp/kpu_gemm.sock（sendmsg 单次唤醒）
             └─ kpu_gemm_daemon.py（python3 常驻，/mnt/data/kpu_llm/）
```

## 五、红线与血泪坑（精选，全量在 AGENTS.md）

**红线**：禁 921600 高速串口；COM16 等非 K230 COM 口严禁打开；所有测试经 safe_run.sh；只动 K230 设备；板上写文件后 sync 再 reboot；WSL 只编译、Windows 做文件/git/adb；PLL 勿动。

**本阶段新坑（每条都是真金白银）**：
1. **nrc=2 契约是 2×2 瓦片**（2 权重行×2 激活行，4 个点积，s[0]/s[1]/s[bs]/s[bs+1] 按 float 偏移）——实现成 2 点积版本 = 偶 token 行全是垃圾，"2.4x 提速"是假数据。判定线索：decode（M=1 奇数）纹丝不动而 prefill 恰好 ~2.4x
2. **Zfh 硬件 fp16**：march 含 _zfh，fp16→fp32 是单条指令且数据随 vle8 进 L1——任何"预转 float 省转换"的方案都是净亏损（预转数组是 71MB/token 的带宽税）
3. **unroll 甜点是 ×4**：×8 爆寄存器（8 条 redsum 链同时存活）反降
4. llama-cli cnv 模式 stdin EOF 无限刷 `> ` 打满单核（曾刷出 621MB 日志）——非交互一律 `--single-turn`（本版无 --no-cnv）
5. safe_run WDT 三坑（v3 已修）：kill 后立刻 V 有竞态；`exec 3<>/dev/watchdog` 失败=非交互 shell 直接死；孤儿 sleep 继承 fd。**v3 设计：喂狗器 subshell 自持 open/喂/V-close + PPID 检测 + EBUSY 降级**
6. adb 后台启动会话回收竞态：`nohup setsid ... &` 后必须**同会话 sleep ≥8s** 再退出
7. daemon 经 adb 起会被掉线 SIGPIPE 杀死——用 `nohup setsid python3 kpu_gemm_daemon.py > /mnt/data/kpwd.log 2>&1 < /dev/null &` + sleep 8
8. 计时仪写 SD 会灌水 2 倍（fflush 队列）——CPU_GEMM_TIMING 日志已改 /tmp（tmpfs）
9. 烧卡一律读卡器（burn_card.ps1），板子 ROM 通道烧大镜像丢数据（历史实锤）
10. 历史镜像手术坑（e2fsprogs metadata_csum_seed、GPT 备份头、262144 扇区=128MiB）见 08-28 旧文档或 git 历史，如再做镜像手术先查
11. **block_q8_0 布局是 {f16 d; int8 qs[32]}——d 在前（offset 0），qs 在 +2**。手写内核若按"qs@0/d@+32"寻址=输出全"？"（本次实锤：微基准自定义结构体 qs 在前，生产 ggml 相反，asm 偏移全错）。正确寻址：pw=qs 指针（base+2），d 用 flh 负偏移 -2
12. **RVV 向量 load 不支持立即数偏移**（只有 `(rs1)` 形式）——子地址必须标量 addi 预计算；且 e8m2 一次 load 占 2 个寄存器，寄存器分配要按组算
13. **vsetivli 的 AVL 立即数最大 31**（"improper CSRxI immediate"）——AVL=32 必须用 `li t6,32 + vsetvli zero,t6` 寄存器形式；prefetch.r 偏移按 32B 粒度编码（T-Head 扩展，320=imm 10）
14. **pkill daemon 后 mmz 段滞留**（CmaFree 不回升）→ 再起 daemon 必挂（mmz alloc 失败崩溃）——杀 daemon 后要 reboot 拿干净池再起
15. PS 管道重编码毁中文脚本：`Get-Content | Set-Content` 会按 GBK 重编 UTF-8（全角标点变 `?`）→ 板上脚本报 unterminated quote。**含中文的脚本一律 write 工具写 + WSL sed 转 LF + adb push**
16. **heap corruption 根因已查明并部分修复**（2026-09-01 bisect）：
    - **根因 A（已修）**：`ggml_kpu_init()` 调用 `kpu_fs_anchor(dir)` → 板上 libstdc++ `std::filesystem::directory_iterator` 析构器损坏相邻堆元数据；与 `gnne_regs` 的 `/dev/mem` mmap 组合触发退出期 `corrupted double-linked list`。bisect 证据：仅设 `KPU_KMODEL_DIR`（空表、无 daemon）即 abort；跳过 fs_anchor 或跳过 gnne_regs 均可消除
    - **修复 A**：移除 `kpu_fs_anchor` 运行时调用（`__attribute__((used))` + 静态函数指针引用保留符号链接 for libllama-common）；daemon 模式跳过 `gnne_regs` preseed（客户端不经 nncase 本地推理，不需要 gnne_regs）；daemon 模式 preload 跳过 CMA 400MB 门槛检查（客户端不分配 CMA，daemon 已占 ~500MB CMA → 旧检查会清空 manifest 导致 0 gemms）
    - **根因 B（残留，不影响生产）**：daemon+preload 模式下 196 个表项（std::string + std::vector<float> 共 ~2.4MB 堆）改变堆布局，暴露 llama-bench/ggml 内部潜在的堆溢出。退出期 abort 仍在（rc=134），但**仅在进程退出时触发，不影响推理正确性或性能**。生产进程常驻不退出，无影响。彻底修复需定位 ggml 内部堆溢出（超出本优化范围）

## 九、2026-09-02 凌晨：接手复核 + 两个负结果（勿重蹈）

接手状态确认：邻居已落地 **Q8_0 nrc=1 手写 asm**（quants.c 内 4 块展开、3 vsetvli/迭代、4 条独立 f32 累加链、flh+fcvt.s.h 用足 Zfh，实测 30 cyc/block vs intrinsics 33）→ **decode tg32 2.59 t/s**；**KPU_LOCAL=1 进程内 runtime**（Path B 落地：heap 版 kmodel + gnne_init，cos=1.0，prefill wall 16.66s vs daemon 23.55s）。

**负结果一：prefill 预载策略死路**（尝试 KPU_PRELOAD=1 + 大 resident）：
- S4 kmodel 实际吃 **5.65MB CMA/个**（文件仅 2.3MB）→ 196 全量 = 1107MB > 1GB 池，**装不下**
- 首载 ~110ms（SD 读主导）vs 重载 ~2.6ms（页缓存）→ 预载把便宜的重载换成昂贵的首载前置，方向错误；resident=100+preload 还会段错误
- 正确策略：resident 保持小（30 级别）+ 页缓存自然热；prefill wall 的主导项是 KPU gemms ~5.8s + CPU 非 GEMM ~8-9s，加载只占 ~1.5s，**常驻调优无意义**

**负结果二：Q8_0 列批处理内核（16 列/调用）三版全废，已回滚**：
- 动机：lm_head 151,936 列 × 每列重载激活行，16 列共享 y 载入 + 摊掉调用开销
- 三版：intrinsics（vsetvli 风暴 1.18 t/s）→ 16 列 asm（GCC "+f" 双计数 36 操作数超限，编译不过）→ 8+8 asm + 4 路 freg 流水（1.22 t/s）
- **根因**：16 路 stride-1088B 的权重流打碎顺序预取，每块 16 次 DRAM 延迟裸露；而"共享 y"本来就被 L1 白送（激活行仅 1088B，逐列处理恒热）。**逐列 asm（顺序访问 + HW 预取）才是本核正解**
- 回滚至 md5 5a44e640（与邻居版逐位一致），tg32 2.57±0.01 确认恢复
- 附带教训：pkill -f 自匹配会杀死自己的 shell 导致漏杀（残留 bench 污染后续测量）；pgrep 验证也要用 bracket 技巧

**当前解码结构账**（2.59 t/s = 386ms/token）：内核 ~155ms（30cyc/block × 8.26M 块）+ lm_head ~90ms（4.86M 块，Q8_0 已是最优逐块成本，量化降级只会更慢——邻居 Q6_K 实验同证）+ 图重建/gallocr/采样 ~60-90ms + 图内非 GEMM ~50ms。**3+ 的唯一剩余杠杆是硬编码 decode 循环（砍图重建/gallocr ~50-70ms）+ 或许 attention 侧 asm**；列批处理此路已证不通。

## 十、2026-09-02 晨：硬编码 decode 循环落地（数值验证通过 + 诚实速度账）

**做了什么**：`llamacpp/src/llama-fast-k230.cpp`（已入 src/CMakeLists.txt）——硬编码 Qwen3-0.6B 风格 decode：token→embed→28×[rms_norm→qkv GEMM→qk-norm→RoPE→attention→o GEMM→rms_norm→gate/up GEMM→silu(gate)×up→down GEMM]→final norm→lm_head。维度全运行时读 hparams（L=28, embd=1024, **head_dim=128 GQA 16q/8kv**（q=2048 宽，wo [2048,1024] 降回）, ff=3072, vocab=151936, theta=1e6, neox）；调度/融合写死；自有 f16 KV 缓存；GEMM 直接调 asm 内核。验证 harness：`.tools/fastk_verify.c` + `build_fastk_verify.sh`（独立二进制，双路对比 logits）。

**验证结果**：**20/20 步 argmax 逐 token 精确一致**，worst maxdiff 0.64（纯浮点累加顺序噪声）。

**速度账（诚实版）**：fast **381.3ms/tok vs 正常 392.6ms/tok**（-11ms，2.9%）。图复用下框架本来就只有 ~11ms 可榨——硬编码循环是正确的基础，但**不是 3+ 的答案**。3+ 要靠：①asm 内核 v2（软件流水/8 块展开，内核 ~300ms 是主体）②fast 路径的标量循环向量化（rms_norm/attention/softmax 目前是标量 C，llama 的 RVV 版更快——这块还在亏 ~10-20ms）。

**排掉的坑（关键语义，勿再踩）**：
- Qwen3 **qk-norm 在 RoPE 之前**（src/models/qwen3.cpp：build_norm→ggml_rope_ext）
- FFN 是 **silu(gate)×up**（ggml_swiglu_split(cur=gate-proj, tmp=up-proj)）
- token_embd/output 是 **Q8_0**（要反量化；output 是独立张量非 tied）
- llama_batch 要手动设 n_tokens；llama_tokenize 传 llama_model_get_vocab(model)
- **-D_GLIBCXX_USE_CXX11_ABI=0 毒药**：libllama.so 是新 ABI，独立 TU 带这 define 会布局错位读垃圾 hparams（h.layer=0xA4000000 即中招）
- 交叉链接 `-llama` 符号链接 ld 跟不了 → 用 `-l:libllama.so.0.3.0` + `-Wl,-rpath-link`
- build-riscv-kpu 裸 `cmake .`（无 env）会静默丢 KPU 源 → 一律走 build_kpu_llama.sh
