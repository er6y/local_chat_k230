# K230 aishell3 VITS KPU 加速 — 交接文档（2026-09-03 轮次）

## 一、本轮目标回顾

延续 aishell3 VITS TTS 的 KPU 卸载工作，把 text_encoder 也搬到 KPU，
进一步降低 TTS 的 CPU 占用，把 CPU 留给 LLM decode。

## 二、本轮完成的事

### 1. text_encoder 静态 bucket（N=64）KPU 化 — 全链路打通

四道墙依次拆掉：

| 障碍 | 解法 |
|---|---|
| mask 链长度由 `tokens_lens` 运行时决定，与静态 64 bucket 广播冲突 | `GreaterOrEqual` 的位置输入换成静态 `arange[1,64]` 常量 `enc_pos_const` |
| pad 位 embedding 垃圾污染尾部卷积窗口 | embedding 查表后立刻把 pad 位零化 |
| 注意力内部 Range/Expand/Reshape 计算链，nncase 把未知维当 -1 参与算术 | onnxsim 常量折叠（1610→715 节点）+ Range 手工折叠 |
| opset-13 Split 无尺寸 → importer 合成 rank-1 `Broadcast(scalar,[2])` 崩 K230 规则 `BroadcastToFakeActivation` | 显式补 `split=[96,96]` 常量到 6 个 conv_module Split 节点的第二输入 |
| onnxsim 把 `tokens_lens` 维度变回符号 N → 板端 "Not fixed shape" | simplify 之后强制钉维 `tokens_lens=[1]`、`tokens=[1,64]`、所有输出也钉死 |

板上实测：
- enc KPU 单句 **38ms**（CPU 334ms，快 8.6 倍）
- 板上与 x86 simulator 对拍一致
- kmodel 5.4MB，路径 `/mnt/data/aishell3/enc_b64.kmodel`

### 2. duration predictor 静态 bucket — 建成并验证，但发现两个关键事实

**事实 A（重要纠错）：text_encoder 不是 CPU 大头，dp 才是。**

实测分项计时（3 句、7.5s 音频）：

| 阶段 | CPU 时间 |
|---|---|
| text_encoder（CPU 路径） | ~24ms/3句 |
| **duration predictor（CPU 动态）** | **696ms/3句（占前端 97%）** |

此前归因错误：把 dp 的耗时算到了 text_encoder 头上。本轮实测拆分纠正。

**事实 B：dp 静态 bucket 在 CPU 上反而更慢。**

| 配置 | RTF | CPU/音频秒 | 说明 |
|---|---|---|---|
| 前端全 CPU + subgen KPU（默认） | **0.202** | **117.5ms (12%)** | 当前板上最优 |
| enc KPU + dp 动态 CPU | 0.217 | 131.9ms | enc 搬 KPU 反而多付 ~100ms 提交开销 |
| enc KPU + dp 静态 CPU | 0.326 | 230.5ms | 静态恒算 64 位置，比动态 L 位置更慢 |

dp 静态 bucket 验证：时长仅 **2.7% 位置变 ±1 帧**（尾差来自 LayerNorm beta 复活 pad 值，比 int8 aishell3 的 +12% 漂移好一个量级）。但 CPU 跑静态 64 位置比动态 L 位置慢。

### 3. dp→KPU 的最后一道墙已定位，未拆

dp 内部 `duration_predictor/flows.{3,5,7}` 用 **`NonZero(mask)→Transpose→GatherND→计算→ScatterND`** 做数据依赖形状的"有效位置压缩"——输出维度=运行时有效位置数，nncase 永远推不出。

深挖后发现：谓词不是简单前缀遮罩，而是**值依赖的耦合流划分**：
- `And(GreaterOrEqual(pred, -5), LessOrEqual(pred, 5))` 分内带/外带
- 两带各走不同变换后 ScatterND 合并
- 内部还有 GatherElements 取枢轴位置 + 四次方程求根的耦合数学

6 个 NonZero 节点，3 个 flow（flows.3/5/7）各 2 个（内/外带）。

旁路方案（未实施）：全画布双分支 + Where 选择，语义完全等价、无动态形状。
但这是至今最难的一刀：数小时、高风险、验证困难（nsd=0 也关不掉耦合变换）。

### 4. 关于"是否值得继续攻 dp→KPU"的成本收益判断（未实测验证）

本轮发现：dp 的 NonZero 是值依赖耦合流，手术难度极高。
而原目标"CPU 留给 decode"可能用调度就能解决：
- TTS 线程挂 `nice 19`，decode 想要 CPU 时立刻抢占
- 12% CPU 在 nice-19 下对 decode 的实际伤害 ≈ 0
- 代价只是 TTS 墙钟从 RTF 0.2 拉长到最坏 ~0.4（仍 <1）

**这个判断原计划用 llama-bench 并发实测验证，但本轮 sshd 反复挂、
WiFi 高负载断连，实测没跑完。下一轮第一件事应做这个实测。**

# 【接续 2026-09-04 凌晨】NonZero 手术完成 + dp kmodel 编译阻塞点

## 完成：NonZero 全画布手术（核心战役）

**dp 的 6 处 NonZero 耦合流（flows.3/5/7 × 内/外带）已全部改写为静态全画布计算，与原始 gather/scatter 机制逐位等价：**

- 语义逆向（用 ORT 扩展输出钩 325 个中间张量 + 图驱动重放）：
  - 流 = 两条直方图（div0 系 H7 / div1 系 H12，公式 `concat(cumsum(0.99*softmax+0.001))×10-5`，前插 0）
  - 内带解码 = 枢轴 `pivot = count(x>=H12)-1` + 7 个按枢轴选列（onehot×ReduceSum 替代 GatherElements）+ 四次方程树（全部逐元素）
  - 外带 = x 恒等透传；最终 `Where(inner_mask, decoded, x)`
  - ScatterND_2..7 原来是幂等写回（写 -5/+5 到端点，本来就在）
- **验证：4 组输入（真实 1 + 合成混合带 3）cos=1.000000、max_abs_diff=0** ✓✓
- 产物链：`tmp/surgery_flow.py`（改写，+fix_surgery*.py 补丁）→ `dp_b64_canvas.onnx`（2035 节点）

## 追加（2026-09-03 深夜 ~ 09-04 凌晨）：校准阻塞破案 + ScatterND 消除

### 1. PTQ 校准阻塞根因（已破）

读源码实锤（kendryte/nncase v2.11.0 标签）：
- C# 侧 `CApi.cs CalibrationDatasetProviderCreate`：把扁平 dataset 按
  `Chunk(n_params)` 切成样本（**sample-major**），再与 `entry.parameters`
  （= 图输入序 [tokens, tokens_lens, speaker, nsd, alpha]）zip 成 `Dictionary<Var, IValue>`。
- python 侧 `PTQTensorOptions.set_tensor_data`：先 `zip(*data)` 转置（**param-major**）再拍平。
- 结论：调用方必须传**参数主序** `[[全部tokens],[全部lens],[全部speaker],[全部nsd],[全部alpha]]`，
  内部转置后恰好是 C# 要的 sample-major。传样本主序就会错位 → "need f32[1] but get i64[1,64]"。
- 隔壁 enc 编译能过正是因为传了参数主序（`samples = [[tks],[tls],[sps]]`）；单输入模型此 bug 不可见。
- 此前试的图序/字母序/倒序/首引序全是红鲱鱼。修复后 `samples_count` 必须用转置前的样本数。
- 教训：nncase 2.9 与 2.11 的 set_tensor_data 行为一致（都转置），多输入+多样本校准必须参数主序。
