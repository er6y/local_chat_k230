### 1.1 关 KPU 的**正确姿势**（踩过的坑）

`KPU_ENABLE=0` **不够**。客户端（libggml-cpu 的 kpu_gemm.cpp）在
`kpu_daemon_on()` 失败且 `KPU_LOCAL` 未设时会掉进 **legacy 路径**——
在 llmd 进程里自己初始化 GNNE、用非 CMA 的 kmodel 缓冲，**会 WDT 硬挂板子
（本会话复现过一次，整机重启）**。必须让客户端 `g_kpu.enabled=false`：
把 `KPU_S16_DIR` 指到一个不存在的目录即可（`ok+ok4==0 → enabled=false`），
这样任何 GEMM 都不会被劫持。

## 2. KPU 数值故障：证据链

### 2.1 工具（已入库）
`chat_service/kpu_probe.py`（板上跑，纯 stdlib，无 numpy）——**直接对
`/tmp/kpu_gemm.sock` 打 GEMM 请求**，用现成的 `*.probe_x/probe_y.npy`
算 cos/maxerr，不经 llmd。用法（在板上）：

```sh
python3 /tmp/kpu_probe3.py l0_down /mnt/data/kpu_qwen/s16_sq 3072 1024
# 输出: mt=256 cos=... ; mt=57 ... ; mt=18 ... ; mt=1 REFUSED
```

### 2.2 实测结果（全部为"错"）

| 配置 | cos | 说明 |
|---|---|---|
| s16b + kpud 23c7c9f2（我编的，尾巴补零） | nan/inf | 输出整个是未初始化 1e32 级垃圾 |
| s16b + kpud 0924bb34（上一版） | ≈0 | \|y\|≈540 量级正常，但完全不对 |
| s16_sq + kpud 0924bb34（**自洽配对**：kmodels 与 probe 同目录同源） | ≈0 | 同上，且首 3 值**与 s16b 完全相同** |
| 上面 + GNNE_CSTAGE/L2STAGE/L2P=1 | ≈0 | pc 翻译成功（p=0x43000000、descriptor repair 3 项），结果仍错 |

**关键判据（9/13 深夜活性测试修正）**：`kpu_liveness.py`（板上
`/mnt/data/chat/`，不依赖参考数据）对 daemon 连打三次 GEMM——`G(x)`、
`G(-x)`、`G(x)`：

```
max|a-c| = 2.1e-14   同输入重复调用：逐位确定（排除陈旧缓冲/竞态）
max|a-b| = 2         换 -x 输出会变（内核响应输入 → 【有在算】）
max|a+b| = 1.2e4     但 y(-x) ≠ -y(x)（不是线性 GEMM）
y[0:4] = 0.2156, 0.2899, 0.3641, 0.4383  （等差数列，明显非 GEMM 形态）
```

→ 早期"输出=输入残留、内核没算"的判断**作废**。正确结论：**内核在算，
但算的图/读的位不对**——候选：fold 输入布局与导出图预期不符、kmodel 导出
图本身错、输出 unfold 读位错（y[0:4] 的等差形态像把某种中间缓冲按错步长
读了）。同输入跨 kmodel 集合（s16b/s16_sq）输出相同，说明权重可能根本没
参与或被同样错位地读。

### 2.3 排除了什么
- **不是部分填充 tile**：mt=256（满载）与 mt=18/57 一样错。
- **不是 kmodel 集合不匹配**：`s16_sq` 自带 probe（自洽）也错；且两套集合
  给出**完全相同**的输出首值 → 输出与权重无关。
- **不是 kpud 版本**：新旧 kpud 都错（新的更糟，输出全未初始化）。
- **不是 pc 虚拟地址问题**：开了 cstage/l2p 后翻译成功，依然错。
- **不是 mmz/CMA 分配**：log 无 `LOAD WARN`，每根 stem 的 CMA 都按模型大小
  正常扣减（`cma A->B->B KB (model N, io M)`）。
- 剩下的怀疑面：**nncase runtime / 输出段（io）这一层**——
  `[gnne] poll: done at iter 0 status=0xc00`（每次都是 iter 0，即查询时 GNNE
  已是 IDLE），runtime 仍报成功并把缓冲交回。

### 2.4 有一条历史线索值得先查
客户端 `kpu_gemm.cpp` 的 **local 路径**（`KPU_LOCAL=1`，把 kmodel 装在 llmd
自己进程里）注释写着 "M1 proven path, **cos=1.0**"——那是 **9/1 era** 的结论。
而 daemon 侧的数值**从没见过 cos≈1 的记录**，era-B（9/10 之后）的一切工作
都是用 `run_perf3.sh` 这类**只测时间、`-n 0` 不生成文本**的脚本量的。
→ 高度怀疑：**KPU 数值从 9/10 era-B 重新导出/改造之后就没再校验过**。
建议第一步就是复现 local 路径（KPU_LOCAL=1 + S4 小 tile + 同源 probe）看
cos 是否还等于 1：如果 local 好而 daemon 坏，问题就锁定在 daemon 的
invoke（持久 inbuf + 每次 input_tensor(copy=true) + to_host/map 的写法）
与 client local 路径的差异上。

## 3. 本会话已修好/已量到的（工程事实，等数值修好即可兑现）

1. **重连风暴（已修，验证过 0 失步）**：daemon 拒绝某 stem 时不排空请求体，
   把残留字节当下一个 magic → 客户端重连 → 风暴。修法：daemon 侧
   `drain_payload` + `send_err(code)`，客户端侧负缓存（`kpu_mark_stem_dead`）
   + 60s 毒化窗口。修前 144 次拒绝→ 72 次失步，修后 103 次拒绝 → 0 失步。
2. **每次调用成本 16.3ms → 6.6ms**：16×16 分块转置折叠/拷出（fold 4.5→1.2ms、
   out 2.3→1.5ms）+ `load_model(copy=false)` 配 mmz/CMA 背板（run 9.1→5.1ms，
   省掉一整个文件大小的重复）。
3. **常驻 cap 50 → 110**（每根 4.6-5.2MB 实测，warm 会按 96MB CMA 地板自动停）。
   注：**按字母序载入**，请求按层序（l0,l1,l2,...）→ l2 及以后反而容易没驻留，
   按层序排序会更合理（下一任可顺手改）。
4. **增量轮 M=18 可以走 KPU**（客户端加 `KPU_S16_MIN` 下界开关，chatd 透传）：
   daemon 实测每 GEMM 4-11ms，而 CPU 侧 M=18 要 21-29ms。**但数值不对，
   所以默认已回 33（=小 M 全 CPU）。**
5. **warm 与 READY 的坑（重要）**：daemon 先打 `listening on` 再 warm
   （~105s），所以 chatd 的 READY 门控（认 "listening on"）会在**能 accept
   之前**就放 llmd 起来 → llmd 启动自检 GEMM 首次 `connect()` 吃
   ECONNREFUSED → `mode=0` 永久缓存 → 掉进 legacy 路径（见 §1.1，会挂板）。
   建议：daemon 先 listen 再打日志（或 READY 认 "warmed"）+ 客户端连不上
   时**不要**走 legacy，直接把 `g_kpu.enabled=false`。

## 4. 板级操作禁忌（本会话踩过的）

- **不要用 `S99chat stop` 后立刻 `start`**：会有残留 chatd/kpud 与新实例并存
  → 双 kpud → 两次 500MB warm → CMA 爆 → 整机重启（本会话复现一次）。
  正确做法：stop 后 `pkill -x chatd kpud llmd kvr_new`，循环等
  `pgrep` 全空，再 start，并用**行号基线**判断 READY（日志是追加，
  旧 "listening on"/"READY"/"warmed" 会造成假就绪——我踩了三次）。
- 手动起 kpud 调试时**必须 `setsid`**，否则 ssh 断开 → daemon 看到
  "parent gone" 自己退出（warm 白做）。
- `pkill -x chatd` 会让 chatd 的孩子（含 kpud）一起走（PDEATHSIG）；
  但 kpud 若已在 accept 里阻塞，需要 `pkill -x kpud` 补刀。
- 板子只能 WiFi（192.168.1.252），无法远程断电；KPU 相关改动务必
  先想清楚会不会挂，挂了就要等人现场。

## 8. 续案（2026-09-13 深夜→凌晨）：死刑推翻 + 两个精确卡点

### 8.1 破案过程（全部可复现，脚本在 chat_service/）

| 实验 | 脚本 | 结论 |
|---|---|---|
| 活性测试 G(x)/G(-x)/G(x) | `kpu_liveness.py` | daemon 输出是输入的**确定函数**（重复调用逐位一致 2e-24、随输入符号变），但不是线性 GEMM |
| 单点扰动扫描 | `kpu_scan.py` | 输出 = **dequant(quant(x))**：y = x + z/s（z/s≈1.2156，int8 回绕周期 2.0）——图首尾的量化/反量化节点在跑，**GNNE 子图本身空转**，权重从不参与 |
| **local 模式自检**（llama-cli + 同一套 .so + 同一批 kmodel） | llama-cli `--kpu --simple-io` + `KPU_SELFTEST=1` | **cos=0.99979**（f32-IO 新导出）/ 0.99741（era-A 旧 s16_sq）；`poll: done at iter 18548`＝GNNE 真跑了 180ms |

**两条铁的结论：**
1. **KPU 硬件、kmodels（新旧两代）、vendor runtime 全部没坏**——llama-cli 进程内
   （local 模式）当天就算出 cos≈1。"KPU 干不了"的判死刑**作废**。
2. kpud daemon 与 llmd 的差别只剩进程上下文：daemon 里 GNNE 核心**从未启动**
   （`poll done at iter 0`，status 恒 0xc00；llama-cli 是 iter 18548、status
   变 0x80000c00）。client 源码注释自证机制：本镜像 /dev/k230-gnne 驱动
   **无 mmap 回调** → runtime 自映射失败 → `gnne_regs` 全局留 NULL → 每个
   k230 子图静默空转。client 的 local 路径靠 **preseed（/dev/mem 映射
   0x80400000 写入 gnne_regs）+ gnne_init()** 救活——llama-cli 里生效，
   **kpud 里同款 preseed（extern 直写 + gnne_init）无效**（输出逐位不变）。

### 8.3 架构切换尝试：llmd 进程内 local 模式（更接近成功）

chatd 加了 `KPU_DAEMON` 开关（0=llmd 进程内 local，1=旧 daemon），llmd 用
**与 llama-cli 完全相同的 .so + env**（KPU_LOCAL=1, KPU_KMODEL_DIR=s16b,
KPU_RESIDENT=CAP16）。llmd 能 READY 且不崩——但**首次 KPU lazy 装载时
SIGSEGV**，两种模式两种崩法（dmesg 全文在 /mnt/data/chat/logs/messages）：

| 模式 | 崩点 | 现场 |
|---|---|---|
| KPU_PRELOAD=1（预载） | 写 0x5c778（只读页，SEGV_ACCERR） | 疑似 nncase 原地补丁 kmodel 时写入不可写映射 |
| lazy（首次 GEMM 装载） | `host_runtime_tensor::create` +0x11E0E8，**调用方传入的 span 指针已是垃圾**（a5=0xa0c4a0c4a0c4a0c4，f16 -1312 的重复模式当指针） | **调用方堆已被踩**——与 client 注释"preseed 与堆布局相互作用（196 表项）引发堆损坏"吻合；llama-cli 只在退出时坏，llmd 更早崩 |

符号化方法（已验证可复用）：
`riscv64-unknown-linux-gnu-addr2line -f -e libggml-cpu.so 0x11E0E8`
（epc − 加载基址 = .so 内偏移，dmesg 的 `in libggml-cpu.so[基址+大小]` 给基址）。

**下一步攻击点（按概率排序）：**
1. **堆损坏修复**：client 的 preseed mmap 加固定远地址提示
   （`mmap(hint=0x3f00000000, MAP_FIXED_NOREPLACE)`）避开堆生长区，重编
   libggml-cpu（inc_build_cpu.sh 半小时）；llmd-local 若活 → 直接就是生产形态。
2. 若还崩：gdb/strace 对比 llama-cli 与 llmd 的首次 create() 调用（重点：
   inp_buf 指针来源、g_kpu 表 196 项的堆状态）。
3. kpud 路线并行留一手：dlsym 版 preseed + `-rdynamic` 重编 kpud（符号实例
   假说一锤定音）。
4. 任何一条通了：llama-cli 的 180ms 首次 invoke 是含一次性 runtime 段分配的，
   稳态 tile 耗时未测（daemon 曾报 5-17ms/调用）——先测稳态再算收益。

### 8.11 内存分段实测账本 + 孤儿 TTS 泄漏 + AUTO/DIO 判决（2026-09-13 14:xx）

**内存分段（/proc/iomem + dmesg + meminfo 实测）**
- 物理 DRAM 2GB（0x00060000-0x7fdfffff），开机即划出 **CMA 1GB @ 0x3FE00000**
  （dmesg: "cma: Reserved 1024 MiB"，cmdline 无 cma= 参数 → 尺寸来自内核
  CONFIG_CMA_SIZE_MBYTES；cma= 是内核早参数，bootargs 加 cma=1280M 可覆盖，
  不必重编内核；u-boot env 在 SD p1，fw_setenv 存在但需配 /etc/fw_env.config）
- 非 CMA 侧 ~950MB：内核 ~80MB + 用户进程
- **为什么隔离**：GNNE/KPU/媒体引擎 DMA 无 IOMMU 散表能力，要求物理连续；
  普通分配器给虚拟连续/物理离散。CMA=预留区域保证 cma_alloc 物理连续，
  空闲时把页借给可移动分配（页缓存）——这就是"CMA 可共用"说法的由来；
  但 **DMA 可分配上限=硬顶 CmaTotal**，mmz/kd_mpi→cma_alloc 只能在这
  1GB 里拿。此前"CMA 没限制可用全部内存"的说法不准确：可共用的部分是
  借出机制，GNNE 可用的是硬顶。
- 纠正一个更早的错误认知：llmd 权重不是页缓存——DIRECT_IO 模式读进
  **匿名内存**（RssAnon 688MB，RssFile 9MB），匿名页不可移动，非 CMA 侧
  塞满后内核把 ~100MB 匿名页钉进 CMA 区域=永久碎片源。

**本轮两个新破案**
1. **孤儿 TTS 泄漏（大！）**：kvr_new --daemon 双 fork 脱管，PDEATHSIG 只
   打到 safe_run 外壳；chatd 每次重启泄漏一个旧守护（~78MB anon + CMA
   kmodel/媒体池）。实测 2 个孤儿共占 **~600MB CMA**——这就是 CMA 账本
   缺口和 rc=134 崩溃循环的根源之一。修复：chatd spawn tts 前 pkill
   -x kvr_new（chatd=929213b1）。
2. **AUTO(mmap) vs DIO(O_DIRECT) 判决**：AUTO 把权重还给可驱逐页缓存，
   消灭"不可移动匿名页钉 CMA"→深装载（F~30-47MB，~180 stems）**不再
   冻结**（2.5h 连续运行含重载+验收），但页缓存锯齿 + TTS 并发合成抢
   CMA → llmd SIGABRT(rc=-6) + TTS rc=134 循环（2s 退避下整机不再复位，
   自愈正常）。DIO 深装载则有 WDT 冻结风险。**过渡态（脏 CMA 上重启）
   是最危险窗口**：本轮又一次 WDT 自愈（干净冷启动每次都稳）。

**定版（板上=仓库）**：LLMD_LOAD_MODE=DIO、KPU_LOCAL_FLOOR_MB=300、
KPU_ENABLE=1、S16_MIN=17、CAP16=110 + 全部护栏（哨兵/毒化/孤儿杀手/2s
退避/warmup 换行）。干净冷启动验证：tts READY → llmd READY → warmup，
CmaFree ~230MB 起。

**满血 9.4 t/s 的两条正道（结论不变，账更清楚了）**
1. bootargs 加 `cma=1280M`（免重编内核；改 u-boot env 或 SD p1，若
   fw_setenv 配不通则读卡器改）+ LLMD_LOAD_MODE=AUTO：CMA 1.25GB 装下
   196 stems(~1.0-1.1GB) + TTS kmodels(~120MB)，权重页缓存在非 CMA 侧
   剩余空间（lm_head 工作集 ~155MB 可容）——需实测 decode 不塌方。
2. 内核 CMA 扩容 + workspace 池共享（长线）。
